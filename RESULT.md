# Краткая информация

- `dataset/` — входные данные, эталоны и кейсы для разработки и тестирования Skill.
- `runs/` — результаты запусков, оценки и отчёты. Результат: `runs/regression/requirements-analysis/{version}/raw/case-{number}/{model}/run-01/workspace/outputs/{result}`.
- `src/` — скрипты выполнения, проверки и оценки Skill.
- Служебные файлы оформляются на английском языке для экономии токенов.
- `skill` — версии навыков 
- Использованные модели `gpt-5.6-sol`, `gpt-5.6-terra`, `gpt-5.6-luna`.

## Методика и источники

Проценты — оценка judge относительно эталона по рубрике кейса. 

Рубрика кейса — правила оценки в `case.yaml`: перечень критериев, максимальный балл каждого и описание уровней качества. Judge сравнивает ответ с требованиями и эталоном и выставляет баллы по этим правилам. Баллы всех критериев складываются, делятся на максимально возможную сумму и умножаются на 100. 

Источники DEV: [v0](runs/regression/requirements-analysis/v0/summary.json), [v1](runs/regression/requirements-analysis/v1/summary.json), [v2](runs/regression/requirements-analysis/v2/summary.json), [v3](runs/regression/requirements-analysis/v3/summary.json), [v4](runs/regression/requirements-analysis/v4/summary.json). Для всех версий совпадают `dataset`; на каждый кейс и модель выполнен один завершённый запуск. Строка «Среднее DEV» — арифметическое среднее трёх DEV-кейсов с равным весом, как усреднение сравнений в [regression.py](src/benchmark/regression.py). Holdout в это среднее не включён. Значения округлены до двух знаков.

## Holdout: финальная версия v4

Holdout содержит один кейс — case-206; поэтому оценка модели совпадает с оценкой этого кейса. Источники: [summary](runs/holdout/requirements-analysis/v4/summary.json), [error analysis](runs/holdout/requirements-analysis/v4/error_analysis.json), [вердикт holdout](runs/holdout/requirements-analysis/v4/holdout.json).

| Модель | Оценка case-206 | Кейсов | Основные замечания judge |

| Sol | 86,00% | 1 | Пропуски исполнителя, полного наименования и терминов; небольшое искажение защищённости питания; чрезмерные неопределённости. |
| Terra | 92,00% | 1 | Сокращённое наименование ОКР, пропуск исполнителя; заданные реквизиты местами оставлены неопределёнными. |

## Основные ошибки

По замечаниям judge в 48 генерациях v0–v4 и holdout. Успешные автоматические проверки не исключают ошибок в содержании.

| Ошибка | Что осталось в v4 |
| --- | --- |
| Придуманы размеры устройства, которых нет в требованиях. | Остаётся у всех моделей в case-202. |
| Пропущены ссылки на стандарты, например RFC 5086 и ITU-T G.742. | Остаётся у Sol и Luna. |
| Не указано, как провести часть испытаний и какие результаты допустимы. | Часть условий и допустимых значений всё ещё требует уточнения. |
| Добавлены лишние разделы, повторения и таблицы. | Документы остаются перегруженными; Luna повторяет разделы в holdout. |
| Неаккуратно оформлены таблицы, подписи и нумерация. | Замечания к оформлению остаются у всех моделей. |
| Изменён смысл требования: дальность связи, обязательность условий или защита питания. | У Sol остаются отдельные неточности. |
| Сокращения объяснены неверно или не объяснены. | Пропуски определений остаются; исправление всех неверных расшифровок не подтверждено. |
| Добавлены незаданные сведения, например город «Москва» и сроки согласования. | Этот пример отмечен у Luna v1; в оценках v4 повторно не отмечен. |
| Недостаточно подробно описаны связи между платами, интерфейсы и режимы работы. | Часть описаний остаётся слишком общей. |
| Пропущены исполнитель, полное название разработки или другие сведения из эталона. | Judge отмечает это в holdout, но часть сведений отсутствует и во входных требованиях. |

Источники: оценки генераций [v0](runs/regression/requirements-analysis/v0/raw), [v1](runs/regression/requirements-analysis/v1/raw), [v2](runs/regression/requirements-analysis/v2/raw), [v3](runs/regression/requirements-analysis/v3/raw), [v4](runs/regression/requirements-analysis/v4/raw), [holdout v4](runs/holdout/requirements-analysis/v4/raw). Примеры дополнительных замечаний: [неверные расшифровки](runs/regression/requirements-analysis/v3/raw/case-201/gpt-5.6-luna/run-01/evaluation.json), [город и сроки](runs/regression/requirements-analysis/v1/raw/case-201/gpt-5.6-luna/run-01/evaluation.json), [неполное описание интерфейсов](runs/regression/requirements-analysis/v3/raw/case-203/gpt-5.6-terra/run-01/evaluation.json). Пометка «уточнить» сама по себе не является ошибкой, если данные действительно не заданы.

## Вывод

С последней версией инструкций **v4 лучше всего работает Terra**: средняя оценка на трёх основных заданиях (dev) — **91,33%**, на тестовом задании (holdout), которое не использовали при улучшении инструкций, — **92,00%**. Если сравнить все модели и версии, лучший средний результат на основных заданиях показала **Sol с версией v2 — 94,00%**.

В среднем по трём моделям лучшие результаты дала **v4 — 90,78%**. Для исходной версии v0 результат составил **90,00%**, для v1 — **89,22%**, для v2 и v3 — по **90,33%**. Таким образом, улучшение инструкций повысило общую оценку на **0,78 процентного пункта**.

На тестовом задании все модели с v4 получили оценку выше установленного порога **80%**. 

Основные проблемы остаются: модели иногда добавляют сведения, которых нет в требованиях, пропускают важные детали, неточно оформляют документ и не полностью описывают способы проверки требований.
