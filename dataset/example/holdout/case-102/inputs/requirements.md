# Требования к генерации ТЗ: сервис уведомлений

## Цель

Подготовить краткое техническое задание на REST API: сервис уведомлений. Результат — один файл `answer.md` в Markdown на русском языке; реализация сервиса не требуется.

## Структура и стиль документа

Обязательные разделы: «Назначение», «API», «Хранение», «Допущения и открытые вопросы», «Критерии приёмки». В разделе API описать входы, успешный результат и ошибки каждой операции. Использовать нейтральные технические формулировки, точные имена маршрутов, полей и значения статусов. Сохранить идентификаторы API на языке интерфейса.

## Функциональные требования и ограничения

- `POST /notifications`: принять JSON с обязательным непустым `message` длиной не более 500 символов, создать уведомление с `read: false`, вернуть его в JSON.
- `GET /notifications`: вернуть JSON-массив всех уведомлений, при отсутствии данных — пустой массив.
- `PATCH /notifications/{id}/read`: установить существующему уведомлению `read: true`, вернуть результат в JSON.
- Отсутствующее, пустое или слишком длинное сообщение и некорректный JSON — HTTP 400; неизвестный id — HTTP 404. Все ответы — JSON.
- Допускается хранение в памяти процесса; сохранение после перезапуска не требуется.

## Неопределённые сведения

Не заданы: формат/генерация id, точные схемы ответов, успешные HTTP-статусы, порядок списка, повторная отметка прочтения и способ подсчёта символов. Обозначить их как `[уточнить]` или открытые вопросы; возможные решения допускаются только с явной пометкой «допущение». Не добавлять обязательные авторизацию, внешнюю БД, нагрузочные показатели или иные неуказанные функции. Конкретные нормативные документы не заданы.

## Требования к итоговому результату

ТЗ должно покрывать все перечисленные операции, валидацию, форматы и хранение. Сформулировать проверяемые критерии приёмки для успешных операций, ошибок HTTP 400/404 и ограничений данных; не копировать готовую реализацию и не скрывать неизвестные значения.
